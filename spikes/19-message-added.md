## Question

Which `messageAdded` records does `users.history.list` return for each kind of mail (received, sent, sent to self, replies, drafts, Spam, Trash, category-labelled, filter-archived or filter-labelled), and what do they contain? Do a record's `labelIds` show the state when the message was added or the state at list time? What do a message's `historyId` and `internalDate` mean, and how should E3 compute the "first classification" flag?

Design text being tested (SD §6.3):

- "Ignore drafts (`DRAFT`), and messages in `SPAM` or `TRASH`. Received and sent messages both count."
- "A thread is marked **first classification** when every one of its messages arrived after the classifier's position." The design doesn't yet say how to compute "arrived after".

### Findings

1. **Record fields.** `messagesAdded[]` entries have exactly one key, `message`. `message` has exactly `id`, `threadId`, and `labelIds`, as expected. Every record also carries `messages: [{id, threadId}]`, which lists the same message as `messagesAdded`. **Records with only `id` and `messages`** (no change array) also appear when several `historyTypes` are requested: `s19_listAll` returned 67 of them out of 117 records, three around each `send`. They didn't appear with `['messageAdded']` alone here, but #20 saw them with `['labelRemoved']` alone. E3 must ignore a record with no `messagesAdded` or `labelsRemoved`.
2. **`labelIds` timing: the labels when the message was added, not at list time.** S09 (moved to Spam), S10 (trashed), and S11 (trashed between two listings) all show `UNREAD, INBOX` on their `messageAdded` record, while `Messages.get` shows `SPAM` or `TRASH`. The later changes appear only as separate `labelsAdded`/`labelsRemoved` records. So filtering on the record catches mail that *arrived* as a draft or in Spam (S07, S08a, S08b), but not mail moved to Spam or Trash before E3 processes it. **E3 must also check current labels when it processes the thread.** It reads the thread for `state` anyway, so this costs no extra call.
3. **Drafts.** `Drafts.create` and each `Drafts.update` add a new message ID (a `messageAdded` record with `[DRAFT]`), and each replaced version gets a `messagesDeleted` record. `Drafts.send` adds a new message ID with `SENT` and no `DRAFT`, in the thread of the last draft version. A draft deleted with `Drafts.remove` leaves a `messageAdded [DRAFT]` plus a `messagesDeleted`. So filtering records on `DRAFT` is right, and the sent message is picked up as ordinary sent mail. Gmail UI autosave wasn't tested; it should look the same (a new ID per save).
4. **Spam on arrival.** Mail that arrives in Spam has a `messageAdded` record whose `labelIds` include `SPAM`: S08a (inserted) and S08b (import's own classifier, which also removed the requested `INBOX`). The record filter drops them correctly. S08c is pending.
5. **Send to self.** One message ID with `SENT`, `INBOX`, and `UNREAD`, not two messages. The same goes for plus-address self-sends (S04a, S05, S07's send).
6. **`historyId` on a message moves on later changes.** The oldest "before" message had `historyId` 36559574, below the start 36559964. After it was marked read, it was 36561312, past the start. So approach (c), "every message's `historyId` is above the position", is wrong: any label change on an old message would make its thread look new.
7. **`internalDate`.** For `send` and `Drafts.send`, it equals the send time, and matches the `Date` header Gmail writes. For `import` and `insert`, it equals the message's **`Date` header**, whatever the setting: D1 (import, default), D2 (import with `internalDateSource: 'receivedTime'`), and D3 (insert, default) were all 3 hours in the past, like their headers. The documented default for `insert` is `receivedTime`, and D2 asked for it explicitly, yet neither was honored through the Advanced Service. Gmail's message IDs are time-based, and D1's ID sorts earlier to match. Google documents `internalDate` for SMTP-received mail as the time Google accepted it; that couldn't be tested here (no outside sender). So `internalDate` is a reliable arrival time for sent and delivered mail, but not for imported mail (for example, a migration tool), where it is the claimed `Date`.
8. **Paging.** `maxResults: 5` gave 5–7 pages per listing. Every record ID was returned exactly once, and no message appeared in more than one `messageAdded` record. The response `historyId` **changes from page to page** while the mailbox is busy: for example 36561100, 36561128, and 36561130 across one listing. Records added during paging do appear on later pages (record 36561102 came after the first page's `historyId` 36561100). So E3 should advance to the **last page's** `historyId`.
9. **Import vs. delivery.** Import threads by headers (`threadId` isn't allowed), applies Gmail's Spam classifier (S08b), and did **not** add categories to non-Spam mail. Whether it runs filters is pending (S12c–S14). The stand-ins were: import for all "received" mail, insert for S04b, S08a, S12b, and D3, and a plus-address self-send for "sent" (S04a, S05, S07). Real delivery to and from a third party wasn't tested.

## Conclusion

- **`messageAdded` filter (SD §6.3).** Keep records for received and sent mail, and drop a record whose `labelIds` include `DRAFT`, `SPAM`, or `TRASH`. It's a cheap first cut, but it is **not enough**: record labels are the labels when the message was added (finding 2). When E3 processes the thread (which it reads anyway), it must use **current** labels. Leave out of `state` any message now in `DRAFT`, `SPAM`, or `TRASH`, and skip the item if no message is left. Category labels (`CATEGORY_*`) are harmless. Ignore records that have no `messagesAdded` or `labelsRemoved` array (finding 1). Advance the position to the last page's `historyId` (finding 8).
- **First classification: approach (a), with no skew margin.** The work item stores the position's `savedAt` at queue time: the time of the `history.list` call whose records queued it. When the thread is first read for processing, it is a first classification if **every non-draft message's `internalDate` is at or after that `savedAt`**. The flag is fixed then and survives retries.
  - (c) is ruled out by finding 6.
  - (b) needs a set of every message ID seen since the position, across runs, which is more state for no gain.
  - No margin: `savedAt` and `internalDate` both come from Google's clocks. And the precision-first rule prefers a missed move to a wrong one: the error case (mail accepted just before `savedAt`, but indexed after it) only loses a move.
- **Edge cases:**
  - A reply to a thread that predates the position has an old message, so it isn't first (S02: correct).
  - A reply to a thread created after the position is first (S03, S05).
  - A draft started before the position and sent after it: `Drafts.send` creates a new message whose `internalDate` is the send time, and the draft versions are excluded. So it's first if it starts a new thread: correct, because the conversation started when it was sent.
  - Imported mail with an old `Date` header (a migration) isn't first, so it gets labels only. That is safe.
  - A message moved to Spam or Trash is excluded before the check.
