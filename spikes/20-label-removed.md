# 20: `labelRemoved` records for a user label

- Task: #20
- Date run: 2026-09-26
- Account: `<test-account>` (consumer)
- Run by: agent via #163, plus two Gmail UI removals by the maintainer

## Question

Does removing a user label such as `Jev/Error` yield `labelRemoved` history records? What is their exact shape, how many records and entries does one removal produce (one per message, or one per thread), and can the `labelId` filter on `history.list` narrow them? E3's retry path (#64, #65) is built from the answer.

Design text being tested (SD §6.3):

- "Filter `labelRemoved` records. Keep only those where `Jev/Error` was removed. These re-queue the thread with its strike count reset."
- E6 adds `Jev/Error` to a whole thread (`threads.modify`), which labels every message in it. The user removes it in the Gmail UI, usually from the whole conversation.

## How it's done

- The label is `E1-20/Error`, a test name that can't clash with a real `Jev/Error` later. Nested-label creation is #25's subject; whether the parent `E1-20` appears is recorded only in passing.
- Threads are made with `Gmail.Users.Messages.import` (`neverMarkSpam: true`), from synthetic `@example.com` senders to `<test-account>`. Replies join by `In-Reply-To`, `References`, and a `Re:` subject. Import rejects `threadId` (`s20_probeImport`), and it returns only `{id}`, so `threadId` is read back with `Messages.get`. Calls retry on the per-user rate limit. They are imported, not delivered; label behavior shouldn't depend on that (finding 9).
- The label goes on each whole thread with `Gmail.Users.Threads.modify({addLabelIds}, 'me', threadId)`, as E6 will do.
- Everything is done through the API except S02 and S03, which are the real user path (the Gmail UI). Whether that differs from the API is part of the question.
- The test account's address is read from `getProfile` at run time and never returned: every result goes through `s20_out_`, which rewrites it to `<test-account>`.

## Functions

`spikes/20-label-removed.js`. Every function takes one optional JSON args object and returns its result (also logged).

| Function | Does |
|----------|------|
| `s20_setup()` | Finds or creates `E1-20/Error` (`Labels.list`, `Labels.create`), imports the S01–S08 threads (subjects `E1-20-Sxx label removal`; S01 has one message, the rest three), and adds the label to each with `Threads.modify`. Returns the label ID, thread and message IDs, and whether a parent `E1-20` label exists. |
| `s20_start()` | Saves `getProfile('me').historyId` as `s20.start`, after the labels are on. |
| `s20_act({only?})` | Runs S01, S04, S05, S06, S07 in order, with a `historyId` checkpoint after each. |
| `s20_list({historyTypes?, labelId?, labelFilter?, startHistoryId?})` | Pages `History.list` from `s20.start`. `historyTypes` defaults to `['labelRemoved']`. `labelFilter: true` filters on the saved label ID (or pass `labelId`). Returns every record's `id` and keys, each `labelsRemoved[]` entry (its keys, `labelIds`, and `message.{id, threadId, labelIds}` with `Object.keys(message)`), any `messagesAdded`, and a per-scenario summary: records, entries, messages covered, and whether they cover the whole thread. An exception is caught and returned. |
| `s20_probeImport()` | Records how import threads a reply: headers only, headers plus `threadId`, `threadId` only, and no `labelIds`. Subjects `E1-20-P …`. Added after the first `s20_setup` failed. |
| `s20_state()` | `Threads.get` (minimal) for every scenario thread: each message's current `labelIds`. |
| `s20_deleteLabel()` | S08: deletes the label (`Labels.remove`, falling back to `delete`, and recording which) while it is still on the S08 thread. Returns the S08 thread before and after. |

Script Properties: `s20.label`, `s20.start`, `s20.map`, `s20.checkpoints`. No triggers.

S08 is a separate function, not part of `s20_act` as the task first sketched, so it runs **after** the first listings. Otherwise the label would already be gone when `s20_list({labelFilter: true})` runs, and finding 6 would be testing a deleted label.

## Runbook

The agent runs every step via #163 (`node spikes/run.mjs run <fn> [json-args]`) unless it's marked **M**.

1. `s20_setup`. Wait about a minute, then `s20_start`.
2. **M** Maintainer steps 1–3. The agent waits for "done".
3. `s20_act`. Wait about a minute.
4. `s20_list`, `s20_list({"labelFilter": true})`, `s20_list({"historyTypes": ["messageAdded", "labelRemoved"]})`, and `s20_state`.
5. `s20_deleteLabel`. Wait about a minute, then run `s20_list` and `s20_list({"historyTypes": ["messageAdded", "labelRemoved", "labelAdded", "messageDeleted"]})` again, with `startHistoryId` set to the S07 checkpoint so the output stays small, to see what S08 produced.
6. Push (`node spikes/run.mjs push`) right before each recorded run, because a concurrent push can briefly restore older code.
7. Record all the returned JSON below.

## Maintainer steps

The agent asks for these in one comment, after `s20_setup` and `s20_start` have run (the threads and the label must exist, and the start position must come first).

1. S02: open the thread `E1-20-S02 label removal` and remove `E1-20/Error` from the whole conversation (click × on the label chip next to the subject).

### Findings

1. **Record shape.** A record is `{id, labelsRemoved, messages}`. Each `labelsRemoved[]` entry is `{labelIds, message}`, where `labelIds` holds the removed label IDs and `message` is exactly `{id, threadId, labelIds}`. `message.labelIds` are the message's labels **right after that change**, not at list time. S02's `UNREAD` record still shows `Label_26`, which a later record removed. This matches #19's finding for `messageAdded`. The `labelId` filter also returned one record with only `id` and `messages`, and the unfiltered `labelRemoved` listing returned 159 of them. So records with no change array also appear when only one type is requested; E3 ignores them.
2. **One record per action, one entry per message.** Each whole-thread removal gave **exactly one** history record, with one `labelsRemoved` entry per message that had the label. That held for the UI (S02, S03), `Threads.modify` (S01, S04, S06, S07), and deleting the label (S08). No record appeared twice. E3 de-duplicates by `message.threadId`: one thread per record, and across records, because the same thread can have other removals in the same window (S02, S05).
3. **UI vs API.** No difference in shape: S03 (UI) and S04 (API) are identical. Opening the conversation in the UI (S02) also marks it read, which adds a separate `labelsRemoved [UNREAD]` record. Only records whose `labelIds` include the `Jev/Error` ID matter.
4. **Trash.** Removing the label from a trashed thread (S06) still gives a record, and its `message.labelIds` include `TRASH`. Trashing also creates `labelsRemoved [INBOX]` records. **E3 shouldn't re-queue a thread whose entries all show `TRASH` or `SPAM`**, because processing ignores Trash and Spam. The entry's labels are enough; no extra read is needed. If the thread leaves Trash later and the label is still off, there is nothing to retry; if it's still on, the next removal re-queues it.
5. **New messages on a labelled thread don't inherit the label** (S07). A message that arrives after `threads.modify` added `Jev/Error` has only its own labels. So E3's rule that "a new message on a flagged thread doesn't queue it" can't look at the new message's `labelIds`. It must check whether **any other message in the thread** still carries `Jev/Error`, using a thread read (`threads.get` minimal, 10 units) for each thread with a new message. Alternatively E3 keeps the flagged thread IDs in state.
6. **The `labelId` filter works, but isn't worth using.** `labelId: Label_26` returned all 7 removals of the label, and nothing unrelated: 10 records instead of 272. It also returned other changes on messages carrying the label (S02's `UNREAD` record, S06's trash record), so the client must still check `labelsRemoved[].labelIds`. The filter applies to the whole call, and E3 reads `messageAdded` and `labelRemoved` in one call from one position. Using it would mean two `history.list` calls, and two positions to reconcile. **Recommendation:** one combined call, filtered on the client.
7. **The combined call works.** `historyTypes: ['messageAdded', 'labelRemoved']` returned both kinds from one call (152 `messagesAdded` records, 113 `labelsRemoved` records, and 159 records with neither), including S07's imported reply as a `messageAdded` record.
8. **Deleting the label does produce `labelRemoved` records**: one record per thread, one entry per message, with `labelIds` holding the deleted label's ID. So a user who deletes `Jev/Error` outright retries every thread that had it, all at once. Afterwards E6 recreates `Jev/Error` with a **new** ID. E3 must match removals against the ID `Jev/Error` had when the records were written. That means keeping the last known ID in state rather than looking the label up by name each run: after a deletion, the name no longer resolves.
9. **Import stand-in.** The threads were imported, not delivered. Label records are about label changes, so import shouldn't affect them. Two import side effects did matter: `threadId` is rejected (see below), and imported messages with an identical subject join one thread (the setup deviation). Neither affects the findings above.

**Import threading** (`s20_probeImport`, 2026-09-26): `Gmail.Users.Messages.import` returns only `{id}`, so `threadId` and `labelIds` must be read back. It rejects a resource `threadId` with `400 threadId not allowed`, with or without reply headers. A reply with `In-Reply-To`, `References`, and a `Re:` subject joins the thread. An import with no `labelIds` gets no labels.

**Rate limit.** The second `s20_setup` attempt failed with `GoogleJsonResponseException: API call to gmail.users.messages.import failed with error: Quota exceeded for quota metric 'Total Query Cost' and limit 'Units per minute per user' of service 'gmail.googleapis.com' for consumer 'project_number:…'`. The runner's own `getProfile` then got HTTP 403 `PERMISSION_DENIED` with the same text. Other spikes were running on the same account at the time, and it cleared within about a minute. `s20_setup` now retries on it.

## Conclusion

`labelRemoved` works for a user label, from the Gmail UI and through the API, and ADR-0004's retry path holds. For E3:

- Read `[messageAdded, labelRemoved]` in one call, without `labelId`.
- Keep `labelsRemoved[]` entries whose `labelIds` include `Jev/Error`'s ID. Use the ID saved in state, so that deleting the label still matches.
- Skip an entry whose `message.labelIds` include `TRASH` or `SPAM`.
- Take `message.threadId` from the entries that are left, de-duplicate across the page, and re-queue each thread with its strike count reset.
- Ignore records with no change array.
- "Still flagged" is a property of the thread: any message in it still carries `Jev/Error`. A new message's own labels don't show it.
